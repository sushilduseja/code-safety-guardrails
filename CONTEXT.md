# Code Safety Guardrails — Context

## Project Identity

**Code Safety Guardrails** is an AI-powered Python code generation tool that wraps a Groq LLM with four security validators. Accepts natural-language prompts (e.g. "write a function to add two numbers"), generates Python code via Groq, and runs it through a `ValidatorPipeline` that detects and auto-fixes security issues before rendering output in a split-pane demo UI.

**Version:** 0.0.1.0 | **Status:** MVP | **License:** MIT

**Audience:** Engineering hiring managers and technical peers evaluating a portfolio project. See `.impeccable.md`.

## Architecture Overview

```
[Browser] ── POST /generate ──► [FastAPI]
                                       │
                                       ▼
                              [Depends() injection]
                          ┌─────────────────┐
                          │ CodeGenerator   │──► [DemoCodeGenerator ─?─► RealCodeGenerator ──► Groq API]
                          │ Telemetry       │──► [AuditAdapter + MetricsAdapter]
                          │ ValidatorPipeline│──► [stateless factory call]
                          └─────────────────┘
                                       │
                                       ▼
                               [ValidatorPipeline]
                                   │  ├─ SQLInjectionValidator
                                   │  ├─ CommandExecutionValidator
                                   │  ├─ SecretsValidator
                                   │  └─ MaliciousImportsValidator
                                   │
                                   ▼
                     GenerateResponse{raw_code, protected_code, passed, issues}
```

Dependencies constructed at startup via FastAPI `lifespan`, stored in `app.state`, injected via `Depends()` (ADR-0008). No module-level globals.

**Key architectural properties:**
- **Zero-dep validator pipeline** — `ValidatorPipeline` is ~60 lines, no external guardrail libraries
- **Deterministic demo mode** — known unsafe prompts bypass Groq entirely via `DETERMINISTIC_DEMO_CODE` dict
- **Fails closed** — any pipeline exception → `passed=False`, protected_code empty
- **Non-streaming** — typewriter effect in UI is visual-only (character-by-character rendering of full response)
- **Single-process** — FastAPI runs uvicorn, SQLite is the only persistence layer

## Domain Glossary

### Core Concepts

| Term | Definition | Notes |
|------|------------|-------|
| **raw_code** | Code generated by Groq before any validation | Shown in left split pane |
| **protected_code** | Code after pipeline validation and fixes | Shown in right split pane; empty if blocked |
| **ValidatorPipeline** | Sequential chain of CodeValidator instances | Each validator runs on the previous validator's output |
| **passed** | Boolean — true if all validators found no issues | `passed=False` even when auto-fixes are applied |
| **fixable** | Validator returns `(False, new_code, msg)` — pipeline applies fix and continues | shell=True→False, secrets redaction, SQL parameterization |
| **blocking** | Validator returns `(False, None, msg)` — pipeline stops immediately | os.system, pickle imports, syntax errors |
| **CodeGenerator** | Seam for code generation — protocol with `generate(prompt, language) → str` | Three adapters: RealCodeGenerator, DemoCodeGenerator, StubGroqClient |
| **RealCodeGenerator** | Adapter that calls Groq API via GroqClient | Wraps normalize_generated_code internally |
| **DemoCodeGenerator** | Adapter that returns canned code from a registry for known prompts; falls back to a wrapped CodeGenerator for unknown prompts | Contains demo bypass logic; registry loaded from external file |
| **CodeGenerationRegistry** | File (`demo_registry.json`) mapping exact prompt strings to canned demo code | Decouples demo data from generator code |
| **AuditAdapter** | Seam for recording audit log entries (SQLite in prod, null in tests) | Stores hashes only; no plaintext prompts |
| **MetricsAdapter** | Seam for recording operational metrics (Prometheus in prod, null in tests) | Per-tenant counts, validator failures, latency percentiles |
| **Telemetry** | Module that combines timing + audit + metrics behind a context manager: `async with telemetry.timed(): ...` | Owns the `time.monotonic()` timing |

### Validators

| Validator | Name | Detection Method | Fixable? | Blocking? |
|-----------|------|-----------------|----------|-----------|
| SQLInjectionValidator | `code/sql_injection` | Regex (f-string, concat, .format) + AST rewrite | Yes — rewrites to `?` parameterized | No |
| CommandExecutionValidator | `code/command_execution` | AST walk + regex (shell=True) | Partial — `shell=True`→False; os.system=block | os.system blocks |
| SecretsValidator | `code/secrets_exposure` | Regex (7 patterns) | Yes — redacts in-place | No |
| MaliciousImportsValidator | `code/malicious_imports` | AST walk (import statements) | No — always blocking | Yes |

### Validator Pipeline Configuration

Validators execute in this fixed order via `create_code_guard(strict=False)`:

```
SQLInjectionValidator → CommandExecutionValidator → SecretsValidator → MaliciousImportsValidator
```

Strict mode (`strict=True`) adds network imports (`socket`, `requests`, `urllib`, `ftplib`, `smtplib`) to the blocked list. Always-blocked modules: `pickle`, `marshal`, `shelve`, `ctypes`.

## Data Flow

### POST /generate — Request Lifecycle

```
1. require_api_key middleware
   ├─ dev/test + no key → tenant_id="dev", rpm=60
   └─ production → SHA-256 hash key, lookup api_keys table

2. slowapi rate limit (tenant_id as key)

3. Check DETERMINISTIC_DEMO_CODE
   ├─ match → skip Groq, use canned unsafe code
   └─ no match → GroqClient.generate_code(prompt)
       ├─ build_prompt() wraps with <SYSTEM_POLICY><UNTRUSTED_USER_TASK> tags
       ├─ AsyncGroq.chat.completions.create(model, temperature=0.3)
       └─ normalize_generated_code() strips markdown fences

4. pipeline.validate(raw_code)
   ├─ Runs validators sequentially, applies fixes to output string
   └─ Returns PipelineResult(passed, issues, validated_output)

5. Asynchronous audit log (asyncio.to_thread, SQLite write)
   └─ Stores: request_id, tenant_id, prompt_hash (SHA-256, never plaintext),
      language, strict, validators_run, issues_found, passed,
      raw_code_hash, protected_code_hash, latency_ms

6. Return GenerateResponse(code, passed, issues, raw_code, protected_code)
```

### Pipeline validate() Semantics

```python
def validate(code: str) -> PipelineResult:
    output = code
    for v in validators:
        ok, fix, msg = v.validate(output)
        if not ok:
            issues.append(ValidationIssue(...))
            if fix is not None:
                output = fix   # apply fix, continue to next validator
            else:
                return PipelineResult(passed=False, issues=issues, validated_output="")
    return PipelineResult(passed=passed, issues=issues, validated_output=output)
```

## Key Decisions (ADRs)

### ADR-0001: Zero-dependency validator pipeline (2026-04)

**Status:** Accepted

**Context:** Needed security validation without pulling in Guardrails AI, LangChain, or similar frameworks.

**Decision:** Build a ~60-line `ValidatorPipeline` with a simple `CodeValidator` protocol. Each validator is a standalone class with a single `validate(code) → (bool, str|None, str|None)` method.

**Consequence:** Lower install footprint (~30 MB), easier to reason about, no external dependency risk. Validators are simple enough that each file is <100 lines.

### ADR-0002: Deterministic demo mode (2026-04)

**Status:** Accepted

**Context:** The demo UI needs to always show validator behavior for security examples, but Groq LLMs may refuse to generate dangerous patterns or may change behavior across model versions.

**Decision:** Maintain `DETERMINISTIC_DEMO_CODE` dict mapping exact prompt strings to canned unsafe code. Before calling Groq, check if the prompt matches; if so, skip the API call entirely and validate the canned code instead.

**Consequence:** Demo is reliable and fast for security examples. Real prompts still hit Groq. New security examples require adding entries to both `DETERMINISTIC_DEMO_CODE` and `SECURITY_TEST_EXAMPLES`.

### ADR-0003: Groq over Gemini (2026-06)

**Status:** Accepted

**Context:** Initial MVP used Google Gemini API. Gemini rate limits were too restrictive for demo usage.

**Decision:** Migrate to Groq API (llama-3.3-70b-versatile, temperature 0.3). Removed all `google-generativeai` references.

**Consequence:** Faster generation, fewer rate limit issues. Requires `GROQ_API_KEY` env var. Llama 3.3 is heavily safety-aligned — it may refuse to generate dangerous patterns even when explicitly prompted, which limits non-deterministic security demo scenarios.

### ADR-0004: Split-pane UI (2026-06)

**Status:** Accepted

**Context:** Users need to see what changed (raw vs protected) to understand the validator's value.

**Decision:** Show Raw Output (left) and Protected Output (right) side-by-side, with pass/fail status and issue count. Responsive: stacks vertically below 768px.

**Consequence:** Makes validator actions visible. When no fix is applied, both panes show identical code, which can be confusing for security test examples where the LLM self-censors.

### ADR-0005: Fails-closed for unexpected errors (2026-04)

**Status:** Accepted

**Context:** An unexpected validator exception or syntax error should not silently pass unsafe code.

**Decision:** Wrap the full generate pipeline in try/except. On any exception, return `passed=False`, empty `protected_code`, and a "pipeline" issue with the error message.

**Consequence:** Safe default for production. The `/audit` endpoint allows operators to investigate failures.

### ADR-0006: CodeGenerator seam with DemoCodeGenerator wrapping RealCodeGenerator (2026-06)

**Status:** Accepted

**Context:** Demo bypass logic (`DETERMINISTIC_DEMO_CODE` dict + inline check) lived inside the generate endpoint, coupling HTTP handling to demo routing. Tests monkey-patched the Groq client.

**Decision:** CodeGenerator protocol seam with `RealCodeGenerator` (Groq), `DemoCodeGenerator` (registry wrapper with fallback), and `StubGroqClient` (test helper). Demo registry stored in external `demo_registry.json`.

**Consequence:** Demo routing concentrates in one adapter. Adding demo prompts requires only editing the JSON file. Tests inject adapters through the seam instead of monkey-patching.

### ADR-0007: Telemetry behind two seams (AuditAdapter + MetricsAdapter) (2026-06)

**Status:** Accepted

**Context:** Audit and metrics were procedural module-level functions with no seam and no test isolation.

**Decision:** Two separate seams — `AuditAdapter` (SQLite/Null) and `MetricsAdapter` (Prometheus/Null) — wrapped by a `Telemetry` module that owns latency timing via `async with telemetry.timed():`.

**Consequence:** Tests inject null adapters — no SQLite or metric state leakage. Format changes affect one adapter.

### ADR-0008: FastAPI lifespan + per-dependency Depends() (2026-06)

**Status:** Accepted

**Context:** Dependencies scattered as module-level globals. Tests monkey-patched.

**Decision:** Construct seams in FastAPI `lifespan`, store in `app.state`, inject via per-dependency `Depends()` in `src/deps.py`.

**Consequence:** Dependency graph visible at startup. Tests override any seam via `Depends()` — no monkey-patching. No module-level mutable state.

### SQLite Schema

**`api_keys` table:** `key_hash TEXT PK`, `tenant_id TEXT`, `rpm_limit INTEGER`, `created_at TEXT`, `revoked_at TEXT`
- Keys are SHA-256 hashed; raw key is shown once on creation
- Resolved via `resolve_key(raw) → hash → lookup WHERE revoked_at IS NULL`

**`audit_log` table:** `request_id TEXT PK`, `tenant_id`, `prompt_hash`, `language`, `strict`, `validators_run (JSON)`, `issues_found (JSON)`, `passed`, `raw_code_hash`, `protected_code_hash`, `latency_ms`, `created_at`
- Prompts never stored in plaintext — only SHA-256 hashes

## Frontend

**File:** `index.html` (served at `GET /`)

**Architecture:** Single-page HTML/CSS/JS app. No framework. API base URL from `window.ENV.VITE_API_URL` or falls back to `window.location.origin`.

**Key behaviors:**
- `loadExamples()` — fetches `GET /examples`, renders safe + security buttons via `DocumentFragment` (no innerHTML)
- `generate()` — `POST /generate` via `fetch` with `AbortController` cancellation
- `streamCode()` — character-by-character typewriter effect (8-20ms/char) on full response
- Ctrl+Enter triggers generation
- `prefers-color-scheme` for dark mode, `prefers-reduced-motion` to disable animations

## Architectural Invariants

- **Pipeline order is fixed.** Validators run in sequence: SQLInjection → CommandExecution → Secrets → MaliciousImports. Each validator's output feeds the next. Reordering changes semantics.
- **fixable ≠ clean.** A validator may (and often does) return `passed=False` even after applying a successful fix. The UI shows "Failed with issues" when any issue exists.
- **No prompt plaintext in storage.** Audit log stores only SHA-256 hashes.
- **Groq is optional for demos.** The deterministic demo mode means the app works without a Groq API key for the predefined security examples.
- **Strict mode only affects imports.** The `strict` parameter only toggles network import blocking. All other validators run identically in both modes.
- **Seams are injected via Depends().** `CodeGenerator` and `Telemetry` are constructed at startup (FastAPI `lifespan`), stored in `app.state`, and injected per-handler via per-dependency `Depends()` functions (ADR-0008). Tests override individual deps without monkey-patching.
- **DemoCodeGenerator wraps RealCodeGenerator.** The `CodeGenerator` seam is a chain: `DemoCodeGenerator(registry, RealCodeGenerator(groq_client))`. Known prompts match the registry and skip Groq; unknown prompts fall through to the real generator (ADR-0006).
- **Telemetry owns two adapters.** `AuditAdapter` (SQLite/Null) and `MetricsAdapter` (Prometheus/Null) are separate seams wrapped by `Telemetry.record()` (ADR-0007).
